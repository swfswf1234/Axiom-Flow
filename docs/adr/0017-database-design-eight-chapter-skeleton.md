# ADR 0017：数据库设计篇改用根侧八章编号体（骨架体裁分治，取代 ADR 0008 决定 2 的适用范围）

状态：Accepted
最后更新：2026-10-22
关联代码：`docs/architecture/database-design.md`（章体本身即契约形状）
关联测试：`tests/contract/test_fixed_document_form.py`（`EIGHT_CHAPTER_SKELETON` 白名单、按体裁的
追溯段边界、`### <table> 列清单` 与 ORM 双向对账）、`tests/contract/test_architecture_documents.py`

## 背景

[ADR 0008](0008-fixed-doc-form-and-metadata-genres.md) 决定 2 把 `docs/architecture/` 契约正文的 H2
**白名单穷举**固定为四段（目的与边界／当前契约／失败与兼容语义／验证与追溯），并由
`test_architecture_documents_follow_four_section_skeleton` 逐等校验。该决定对 `overview.md`、`api.md`、
`code-map.md` 一直成立且有益，但对 `database-design.md` 出现了它自己没预料到的用法冲突：

- 三项目共用一个库，`af_*` 的形状必须能与根仓库总纲 `QED-Engine/docs/architecture/database-design.md`
  **按章对读**。总纲用的是八章编号体（前言／规则／总览／整体架构／详细设计／同步契约／变更运维／守护），
  且它的三章总览行、4.4 读写矩阵、6.3 路由行是跨项目同步时点名的位置。四段体把这四类内容压进
  「当前契约」一段，对账时只能靠人眼在两篇文档间跳。
- 用户 2026-10-22 点名要求本篇「按八章结构重新梳理一遍」。[PLAN-024](../history/plans/2026-10/2026-10-21-af-table-family-rebuild.md)
  的「骨架冲突与本案裁决」节当时把这一项记为**未采备选**并写明「若用户后续点名要八章，另批立项」，
  本 ADR 即那一次另批。
- 不改规则就改文档会直接撞守护：H2 序列逐等校验立即转红。所以这是 `standards/` 的实质规则变更，
  必须先立 ADR，再同批改治理规范正文与守护白名单。

## 决定

1. **骨架按体裁分治，不再全局统一**。`architecture/` 分两种骨架，各自有 H2 白名单，顺序固定、
   穷举校验，多一段少一段都转红：
   - **四段体**（`overview.md`／`api.md`／`code-map.md`）：`目的与边界 / 当前契约 / 失败与兼容语义 /
     验证与追溯`，取值与校验函数一律不变。
   - **八章编号体**（`database-design.md`，唯一适用篇）：`一、前言 / 二、遵循的规则 / 三、本项目表总览 /
     四、整体架构（本项目所需部分） / 五、详细设计 / 六、与 QED-Engine 的交互与同步契约 /
     七、变更与运维 / 八、守护与验证`，章名与总纲逐字同形，使两篇可按章对读。
2. **追溯段边界随体裁移动**：八章体的末章「八、守护与验证」承担原「验证与追溯」段的角色——
   任务编号（`REQ-`/`PLAN-`/`ARCH-`/`DEFECT-`）与具体日期只允许出现在第八章，一~七章仍是零过程叙述的
   契约正文段。ADR 0008 决定 3 的**规则本身不改**，只改它对本篇的锚点。
3. **可对账锚点与章号解耦**：`### <table> 列清单`、`#### METHOD /path`、`### 端点总表` 这类被守护解析的
   小节标题**不因改章而改名、不降级**（列清单锚点固定在第五章内）。改章只动 H2 归属，动一条锚点即
   对账失效。
4. **章体改动不得增删事实**：重排只允许「搬位 + 连接句」，条文、判据、代价、例外、列清单逐条零丢失，
   并以搬运前后的表行首格与反引号 token 集合比对作为零丢失证据。

## 后果

- **正面**：`af_*` 与根侧总纲可按章对读，跨项目同步时能指名位置（三章总览行 ↔ 本篇三章、
  六章同步契约 ↔ 总纲 6.2/6.3）；「内容按总纲补齐、骨架守四段」的折中口径消失，体裁冲突有据可判；
  其余三篇的形状完全不受影响，ADR 0008 的其余决定（三体裁元数据、契约表双向对账、守护不钉措辞）继续有效。
- **代价**：`architecture/` 不再有一种统一形状，读者需要知道哪篇用哪种骨架；守护从一份白名单变两份，
  追溯段边界也要按文档取；本篇正文内的交叉引用需从「段名」改口为「章名 + 节名」。
- **缓解**：两种骨架各自被穷举校验，体裁分治的规则正文写进
  [文档治理规范](../standards/doc-governance.md)「固定文档骨架与可对账契约」节（唯一正文），
  本 ADR 只记录为什么分治；`docs/architecture/index.md` 的登记表标注每篇骨架；
  追溯边界由 `_contract_body()` 按文档名取，不需要人记。

## 取代

**部分取代** [ADR 0008](0008-fixed-doc-form-and-metadata-genres.md) 决定 2 与决定 3 的**适用范围**：
决定 2 的「固定文档统一四段骨架」改为「四段体为默认，`database-design.md` 用八章编号体」；
决定 3 的正文去日期化规则、取值枚举与「追溯段允许归档壳式来源」全部原样保留，只是本篇的追溯段
换成第八章。ADR 0008 决定 1（三体裁元数据）、决定 4（契约表必须可对账）、决定 5（守护只校结构与枚举）、
决定 6（版本末期统一转正评审）不变，本篇的元数据体裁仍是契约正文类。

标准正文：[文档治理规范](../standards/doc-governance.md)「固定文档骨架与可对账契约」；
执行承载：[PLAN-024](../history/plans/2026-10/2026-10-21-af-table-family-rebuild.md) 的 W14 节。
