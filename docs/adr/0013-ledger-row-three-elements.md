# ADR 0013：台账行的三要素（任务描述、具体终态的成功标准、唯一承载文档指针）

状态：Accepted
最后更新：2026-09-30
关联代码：`docs/trackers/todo.md`（表列与「规则」节）、`docs/standards/task-lifecycle.md`（列契约）、
`docs/trackers/project-status.md`（引用台账列名处）
关联测试：`tests/contract/test_tracker_governance.py`（新列名、纯指针断言、成功标准禁词与禁日期断言）

## 背景

台账表原七列 `ID / 类别 / 优先级 / 状态 / 任务 / 关闭条件 / 证据/下一条件`，实践中三处失衡
（直证取自 2026-09-30 的本轮台账整理）：

1. **「证据/下一条件」承载了三种互相冲突的东西**：承载指引、最新结论、日期化裁决史。三者混在一列
   导致同一事实在 `todo` 行、承载计划、`completed.md` 三处各自漂移。实测判例：PLAN-019 行长期写
   「Q1~Q10 待评审」，而其承载壳同一时期已是「W0/W1 完成」＋悬置项 `Q2/Q4/Q6-a/Q7/Q9~Q11`
   ——行落后于壳，且落后无人发现，因为该列没有守护能判出语义过期。
2. **列界与语义倒置**：判据列上限 80 字，历史列上限 200 字 ⇒ 读表者最先读到的是流水账，
   「做什么」与「怎么算完成」反而被压到最短。同轮的节首段落里 REQ-095 与 ARCH-034 的关闭叙述
   出现两次（同一段落自我重复），是同一失衡的文档面表现。
3. **「关闭条件」被当进度字段使用**：列名回答「怎么关」，实际内容写「到哪了」。用户在 2026-09-22
   已要求「事项与成功标准一经评审固定，不得随进度翻转」，但表内没有任何一列名承载这个语义，
   该要求只存在于口头，无法守护。

首轮落地（本 ADR 初版把第三列定为「文档指引＋一行现状 ≤100 字」）经用户 2026-09-30 评审后仍有两处
残余错位，故本 ADR 以现文本为准并同批收口其实现（未提交前修订）：

4. **指引列仍带散文**：「一行现状」把「W0/W1 完成」「待裁悬置项清单」这类会腐化的进度叙述留在表内，
   与承载计划的工作项表构成第二事实源；列名「承载/现状」自证了这种混合。
5. **成功标准写成了验收流程而非终态**：实际读数是「S1~S6 逐条实施带契约测试且全量门禁绿
   （真机面＝承载壳 W9）」——它回答「按壳里哪几条判据验收」，不回答「完成时系统长什么样」，
   读者必须打开壳才能知道这件事交付什么。

第二轮落地（指针列 ≤3 个链接、镜像行的壳链接仍在「任务」列开头）经用户 2026-09-30 第三轮评审后
仍有两处冲突，本 ADR 以现文本为准并同批收口其实现（未提交前修订）：

6. **「去哪读」有两个说法**：计划镜像行的承载壳链接写在「任务」列开头，而「承载」列填的是
   `design/`/`architecture/` 文档——同一行的承载指引分裂在两列，读者无从判断哪一篇是本行的事实源。
7. **多篇指针构成第二事实源**：一篇 `design/` 条文与一个计划壳同时挂在行内，两者对同一件事的表述
   会各自漂移（漂移不可判出，与背景 1 同型）。**承载必须是一篇文档**：设计/架构文档的引用已由承载
   文档自身的「关联设计／关联 ADR」元数据登记，台账不重复登记。

## 决定

1. **三列固定语义并改名**（其余四列 `ID/类别/优先级/状态` 不变；本决定取代 ADR 0006 的列名表述）：
   - `任务`＝**任务描述**：这件事到底做什么，按承载计划的「工作项」列出范围（做什么＝W 几到 W 几、
     落哪张表/哪个端点/哪个模块），不写日期与进度，**不放任何文档链接**（文档链接只在「承载」列出现，
     守护对「任务／成功标准」两列断言无 markdown 链接）。跨项目入站请求的
     `**请求接收（来源仓库 REQ-xxx）**` 标记写在本列句首。
   - `成功标准`（原「关闭条件」）＝**完成时的具体终态**：谁做什么、什么落哪张表/哪个端点/哪个产物，
     可检验且不依赖打开别处文档；≤80 字；**一经评审固定，不随进度改写**。
     **禁止验收流程措辞**（守护禁词：`门禁`、`收口`、`全绿`、`成文`，以及 `S1~S6` 这类壳内判据区间
     引用——它们属于计划壳「验证与验收」节）。写不出成功标准的诉求不得成为任务行。长期行写
     退出/立项条件；主线聚合行写其支线终态的合取。
   - `承载`（原「证据/下一条件」「承载/现状」）＝**唯一承载文档指针**：**恰好 1 个** markdown 链接、
     **不含任何自然语言**（守护判据＝剥去链接与分隔符后残余为空，且链接数 == 1）。链接指向本行的
     承载文档：计划镜像行＝其自身计划壳（链接文本＝壳 H1 标题，标题与状态由镜像守护断言同步）；
     支线行＝其 `../plans/*.md` 承载壳（共享计划的多行可指向同一篇）；主线聚合行＝本轮的登记台账壳；
     长期行＝其治理文档（`standards/` 或 `roadmap.md`）。`design/`、`architecture/` 等被涉及的文档
     **不在本列登记**，由承载文档自身的「关联设计／关联 ADR」元数据给出，避免同一事实两处漂移。
     现状与描述一律活在指向的那一篇文档里。
2. **日期与细节只活在 `plans/`**：裁决全文、勘察记录、门禁读数、逐日执行日志与「到哪了」一律写入
   承载计划（或承载节），关闭后的证据入 `completed.md`；`todo` 表内**禁止出现 ISO 日期字面量**
   （判据：剥去 markdown 链接目标后三列均不得匹配 `\d{4}-\d{2}-\d{2}`）。此规则是 ADR 0006
   「进度单源」的收紧，不是新增方向。
3. **承载纪律收紧、位置统一**：一任务一行（ADR 0011）继续有效；一任务一承载（ADR 0006）由
   「在『任务』或『承载』列引用计划」收紧为**只在「承载」列以唯一指针引用**。计划镜像行按 ID 前缀
   `PLAN-*` 识别（不再靠「任务」列的链接前缀），其「承载」列单链接的链接文本＝壳 H1 标题、目标＝
   `docs/plans/` 下的活跃计划文件，标题与 `状态：` 逐字同步由镜像守护断言；支线行的唯一指针必须指向
   `../plans/*.md` 且该壳登记本行 ID（「关联 Tracker」或 `## 承载 <本行ID>` 节）；主线聚合行仍须在
   「任务」列列全支线行 ID。
4. **守护落地**：`test_tracker_governance.py` 断言四件事——成功标准列界与禁词、承载列唯一指针
   （剥链接与分隔符后残余为空**且链接数 == 1**）、三列剥链接目标后禁 ISO 日期、「任务／成功标准」
   两列无 markdown 链接；镜像与聚合行判定改按 ID 前缀（`PLAN-*` 为镜像行）。
   实施按先红后绿＋变异复验（承载列加第二篇链接／把壳链接挪回「任务」列／承载列塞散文／
   成功标准用禁词／注入日期 ⇒ 对应用例各转红一次后当场还原）。

## 后果

- **正面**：表回到纯导航——三眼看清「做什么／完成时长什么样／去哪读」，且「怎么算完成」这一列
  第一次真正回答终态而不是流程；**一行只有一个承载文档**，「去哪读」不再有两种说法，优化工作只沿
  承载文档推进；进度叙述只剩计划壳一处，行不可能再落后于壳；指针列可被机械判定是否退化
  （散文一进来就红，第二篇链接一进来也红）。
- **代价**：进场读台账时拿不到现状、也看不到涉及的 `design/`/`architecture/` 文档，必须先打开唯一
  承载文档再顺其「关联设计」跳转（这是本决定的目的而非缺陷）；粗粒度进度只剩「状态」列三态；
  历史归档文档、`completed.md` 已关闭行与本 ADR 之前的若干文档仍用旧列名「关闭条件/证据」叙述，
  不回改（当时记录）。
- **缓解**：承载计划的「工作项」表与「用户裁决登记」节本就是细节唯一事实源（ADR 0006）；
  `completed.md` 继续承载关闭后的全部判据与读数，信息不丢只搬家；「状态」列三态＋指针足以定位下一步。

## 取代

取代：[ADR 0006](0006-ledger-plan-carrier-contract.md) 中与台账**列名与列语义**有关的表述
（决定 3「关闭条件成文」、决定 4「『证据/下一条件』列只保留最新一条状态结论＋指向承载位置的引用」）
——语义保留并收紧为「成功标准＝具体终态＋承载列＝唯一承载文档指针」；其决定 2「每个 todo 行必须恰好
声明一个承载位置」不变，本 ADR 只是把该位置固定为「承载」列的单个链接；ADR 0006 的其余决定（一任务一承载、进度单源、`In Progress` ≤3、DEFECT 前缀退役）
**继续有效**。[ADR 0011](0011-ledger-one-row-per-task.md) 一任务一行不变，其请求接收标记所在列
由「证据/下一条件」改到「任务」列。
