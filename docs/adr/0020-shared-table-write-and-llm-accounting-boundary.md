# ADR 0020：共享表业务写入与调用记账边界

状态：Accepted
最后更新：2026-11-26
关联代码：`src/axiom_flow/engines/kp_gateway.py`、`src/axiom_flow/orchestrator/jobs.py`、`src/axiom_flow/db/llm_ledger.py`
关联测试：`tests/contract/test_design_documents.py`、`tests/contract/test_fixed_document_form.py`、`tests/unit/test_engine_kp_gateway.py`、`tests/unit/test_db_llm_ledger.py`

## 背景

共享 `qed_*` 表服务多个项目。表前缀、结构定义与迁移维护说明谁负责 schema，不等于谁独占业务数据写入；把两者混为一谈会错误禁止合法的跨项目写入。另一方面，`qed_llm_calls` 同时承载花费、调用次数与执行归因，同一笔调用由调用方和网关各写一行会直接造成重复记账。

既有 `af_kp` 提升是 8900 拉取式只读导出，该通路的单向约束只适用于提升本身，不能扩展成 Axiom-Flow 对所有共享主表的永久禁写。课程级章总结与两段学习导读需要由 AF 按显式目标身份直接更新共享知识点行，因此必须把业务写入权、提升方向与调用记账责任分别定清。

## 决定

1. **共享表按契约跨项目读写**：共享 `qed_*` 表允许各项目按已确认契约执行业务 DML。8900 是共享表结构定义与维护方，表前缀和 schema 所有权不等于业务写入独占权；`qed_knowledge_point` 不是 8900 的唯一业务写表。
2. **结构变更仍走所有权流程**：业务 DML 权限不授予自行 ALTER、DROP 或重建共享表的权限。共享表结构变更仍先改根侧总纲，再由所有权方执行迁移并通知消费方。
3. **`qed_llm_calls` 是记账治理例外**：生产调用账统一由 8900 写入，一次调用只落一行；AF 不重复直写同一笔。文本网关出站声明 `accounts_externally=True`，AF 的本地账本包装器在该通路不启用。
4. **本地追加写器不是生产记账通路**：既有 `LlmCallLedger` 只保留给显式隔离测试和历史兼容验证，不构成生产写入授权；新增或改造生产调用腿不得使用它写 `qed_llm_calls`。调用记录只追加，表结构绝不 DROP 重建。
5. **提升与课程级直写分路**：既有 `af_kp` 提升继续由 8900 拉取式单向消费，AF 提供只读导出且不回写提升结果。课程级章总结与导读是 AF 的另一条明确写腿，按显式 `chapter_kp_id` 更新共享主表的课程级 outline 行，并守身份、确认态、证据哈希与同事务约束。
6. **重启不依赖记账边界变化**：服务启动仍不依赖 8900 在线；解析图像槽位继续直连模型服务。调用是否直连与生产账由谁写是两个问题，图像直连不恢复 AF 自写生产账的旧语义。

## 后果

- **正面**：跨项目业务写入有明确授权，提升腿的单向性不再被误读为全局禁写；调用账仍保持单一生产写者，避免重复花费与归因。
- **代价**：AF 课程级直写必须自行保证目标身份、确认保护、幂等与回滚；8900 网关当前没有幂等键，不确定重试只能先查已有调用账并核对原请求后恢复，不能声称 exactly-once。
- **缓解**：共享表直写与调用账分别设反向守护；本地账本写入器仅用于隔离测试；课程级腿以显式 `kp_id`、证据哈希和行内复核收敛并发写。
- **边界**：本决定不改变共享表列形状，不授权 AF 执行 DDL，不要求根侧另建课程级生成链，也不改变既有提升的拉取方向。

## 取代

- 部分取代：[ADR 0004](0004-model-boundary-and-pipeline-ownership.md) 决定 6 中「图像槽位由本仓库自写 `qed_llm_calls`」的旧语义；模型直连、生命周期归 8900 与解析管线归本仓的决定不变。
- 补充：[ADR 0016](0016-af-family-rebuild-into-four-tables.md) 的 `af_*` 表族边界；共享表的业务 DML 不由该表族封闭。
