# ADR 0015：标准作为治理事实源与变更门禁

状态：Accepted
日期：2026-07-29
领域：工程治理
决策阶段：v0.3
取代：—
被取代：—

## 背景

`AGENTS.md`、standards、guides、templates 和 ADR 当前重复维护部分任务、文档和追溯规则，规则
修改后容易只同步其中一处。四份标准的元数据与正文结构也不一致，人工无法快速判断治理对象、
决策依据和自动门禁。现有任务分类还把所有远端推送都归为 D 类，严格执行会让每次普通源码交付
额外产生一份没有独立审计价值的发布计划。

## 决定

1. `docs/standards/` 是工程治理规则的唯一事实源；根 `AGENTS.md` 只保留 Agent 快速路由、问题
   定位和完成检查，具体规则必须链接到对应标准。
2. 保留任务生命周期、文档、ADR、代码与文档追溯四份稳定标准。每份标准统一声明状态、最后
   更新、治理对象、依据 ADR 和关联测试，并包含目的与边界、强制规则、执行与门禁、变更与取代。
3. 能由仓库确定性判断的核心规则必须有自动化测试；不能可靠自动化的规则必须在实施计划中声明
   人工验收、证据和责任位置。
4. 改变标准的治理对象、强制规则、事实源或门禁属于实质变更，必须先新增 ADR。措辞、链接、
   勘误和不改变语义的结构整理可直接修改标准并通过对应门禁。
5. 普通分支或 `main` 的源码提交与推送属于原任务的交付步骤，不单独归为 D 类。创建或移动标签、
   GitHub Release、部署、受保护环境变更、正式数据操作和其他需要独立回滚的发布动作仍属于 D 类。

## 后果

Agent 和开发者从 AGENTS 快速进入任务，再以 standards 判断强制规则，避免双重权威。统一契约与
双向测试映射增加少量维护成本，但能直接发现遗漏。普通源码交付不再制造空洞的 D 类计划；具有
独立发布或数据风险的操作仍需单独计划和人工复核。
