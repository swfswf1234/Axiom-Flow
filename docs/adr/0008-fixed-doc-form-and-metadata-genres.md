# ADR 0008：固定文档的体裁化元数据、统一骨架与可对账契约表

状态：Accepted
最后更新：2026-09-23
关联代码：`docs/standards/doc-governance.md`、`docs/architecture/`、`docs/design/`
关联测试：`tests/contract/test_fixed_document_form.py`（体裁元数据、四段骨架、正文去日期化）、
`tests/contract/test_architecture_documents.py`（端点与列清单对账）

## 背景

`docs/design/` 经 PLAN-012 有了同构骨架与就地条文编号，`docs/architecture/` 仍是三种形状并存：

- **元数据三套写法**：`overview/api/database-design` 用「设计状态 + 实现状态 + 确认状态 + 关联\*」，
  `code-map.md` 用「`状态：Current`」，`index.md` 只用「状态 + 最后更新」。而
  [文档治理规范](../standards/doc-governance.md)「元数据」节只写了「架构和设计声明设计状态、实现状态……」，
  **没有为映射类与索引类规定形状**，所以 `Current` 是一个不在任何枚举里的自造取值，偏离也无据可判。
- **正文混入过程叙述**：固定文档里散落数十行 `REQ-nn` / `PLAN-nnn` / `ARCH-0nn` / 具体日期的台账式
  叙述（治理规则要求日期化过程只写承载文档）。代价已经显形：`database-design.md` 的表清单仍写
  「待真机迁移 0002」，而同文档头部声明 `Verified`——**门面说完成、正文说待办**。
- **事实源重复**：`code-map.md` 的「备注」列长成第二份实现正文（单格最长约 1500 字，复述编排判据、
  守卫次序与判例），而治理规范给它的定位是「代码/设计/测试映射的唯一事实源」。
- **守护钉措辞**：契约测试把具体历史字符串与 commit 锚点写进断言，端点清单靠硬编码字符串锚定，
  改词必改测试，且「文档说完成、正文说待办」这类矛盾无人能自动发现。

## 决定

1. **元数据按体裁分三类**，取值仍只用治理规范已有的枚举：
   - **契约正文类**（`architecture/` 的 overview、api、database-design 与 `design/` 三篇）：声明
     `设计状态`、`确认状态`、`实现状态`、`最后更新`、`关联代码`、`关联测试`、`关联 ADR`。
     `实现状态` 一行只允许「枚举值 + 至多一个未达条件从句」，从句内**不得**出现任务编号或日期。
   - **映射与索引类**（`architecture/code-map.md` 等登记表）：声明 `状态`（只允许 `Current` /
     `Superseded`）、`确认状态`、`最后更新`、`覆盖范围`；**不得**声明 `设计状态` / `实现状态`
     （映射表不是方案，无「实现与否」可言）。
   - **目录索引类**（各目录 `index.md`）：只声明 `状态` 与 `最后更新`，纯导航、无正文事实。
2. **固定文档统一四段骨架**，与 `design/` 的六段对称：`## 目的与边界` / `## 当前契约` /
   `## 失败与兼容语义` / `## 验证与追溯`。H2 顺序固定、白名单穷举，缺段即守护转红。
3. **正文去日期化**：固定文档的**契约正文段**（`architecture/` 与 `design/` 中除末段追溯段以外的
   全部段落）不得出现任务编号（`REQ-`/`PLAN-`/`ARCH-`/`DEFECT-`）与具体日期；来源与判例一律降级到
   末段追溯段（`architecture/` 的 `## 验证与追溯`、`design/` 的 `## 追溯`）。追溯段沿用既有的
   「来源：PLAN-0xx（已归档）」写法并链接 `docs/history/` 归档壳，但**不得**指向已归档壳的条文编号
   （[PLAN-012](../history/plans/2026-09/2026-09-23-design-narrative-framework.md) 的 R2 裁决不变）。
   日期化过程的事实源仍是 `trackers/completed.md` 与承载计划。
4. **契约表必须可对账**：`architecture/api.md` 每个端点一节，节标题固定为
   `#### METHOD /path`（四段骨架占 H2、接口四类占 H3，故端点节落在 H4；管理面端点同形但单独成节、
   **不进**公共契约总表）；
   `architecture/database-design.md` 每张表一张列清单表。守护以**运行态真源**（FastAPI `app.routes`、
   SQLAlchemy `Model.__table__.columns`）双向对账：文档有码无、码有文档无，两侧都判失败。
5. **守护只校结构与枚举，不校措辞**：不得把历史字符串、commit 锚点或具体用例名写进断言；
   新增守护必须逐条做变异转红复验。
6. **版本末期统一转正评审**：一个版本收口时，`architecture/` 与 `design/` 正文的 `确认状态` 必须
   逐篇核对并统一处置（转「已确认」或写明留在「暂定」的评审项），不得出现同目录内权威等级
   随机不一致。本决定不改变治理规范既有的转正触发条件与「用户发起回退」条款。

## 后果

- **正面**：`architecture/` 与 `design/` 的形状可被守护穷举而非靠人眼；「门面说完成、正文说待办」
  这类自相矛盾成为编译期失败；`code-map.md` 回到纯映射，行为判据只在 `design/` 条文表出现一次。
- **代价**：三篇固定文档与两套守护同批改写，diff 规模大；节标题固定为 `#### METHOD /path` 后端点
  层级变深；来源从正文挪到「追溯」段后，读者要跳一次才能看到判例。
- **缓解**：端点按四类（公共契约）+ 非公开管理面分组，分组标题是 H3、每组前有分类总览表，
  读者不必在 H4 列表里自己归类；`design/`
  条文表已含「实现落点 → 守护测试」，`code-map.md` 只反向指条文编号，不重复任何判据；对账守护从
  运行态取真源，改写文档时被守护立即纠正，无需人工比对。

## 取代

不取代任何既有 ADR。[ADR 0003](0003-standards-governance-alignment.md) 建立的治理体系仍然有效，
本决定只补它欠定义的「体裁」维度并细化「版本末期整理」的判据。承接本决定的标准正文是
[文档治理规范](../standards/doc-governance.md)「元数据」「固定文档骨架与可对账契约」「版本末期文档整理」
三节；执行承载是 [PLAN-014](../history/plans/2026-09/2026-09-23-arch010-v01-architecture-form-normalization.md)。
