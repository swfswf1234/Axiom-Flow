# ADR 治理规范

状态：Current
最后更新：2026-07-29

## 适用边界

ADR 只记录会改变系统边界、公开 API、持久化语义、事实来源、解析路由或高成本工程约束的
决定。架构文档描述当前结构，设计文档描述接口与验收，计划描述实施步骤，实验报告提供外部
模型证据；这些内容不得由 ADR 重复维护。

## 编号与路径

- 文件名固定为 `NNNN-lowercase-slug.md`，编号在整个仓库中单调递增且进入主分支后永不复用。
- ADR 保持在 `docs/adr/` 扁平目录，不按年份或产品版本移动；版本只记录为决策阶段。
- 新 ADR 使用当前最大编号加一，并在同一变更中登记 README。并行分支冲突在合入前重新编号。
- Superseded 和 Rejected ADR 原位保留，不能移入 history 或删除。

## 元数据

每份 ADR 在标题后按顺序声明：`状态`、`日期`、`领域`、`决策阶段`、`取代`、`被取代`。

- 状态只允许 `Proposed`、`Accepted`、`Rejected`、`Superseded`。
- 领域只允许 `解析与评测`、`数据与持久化`、`API 与任务`、`审阅与发布`、`工程治理`。
- 决策阶段使用 `v<主版本>.<次版本>`，只表示决定首次形成的阶段，不限制后续版本继续适用。
- 没有取代关系时写 `—`；存在关系时使用指向原文件的 `ADR NNNN` Markdown 链接。

## 状态与取代

`Proposed` 可变为 `Accepted` 或 `Rejected`，`Accepted` 可被后续 Accepted ADR 完整取代并变为
`Superseded`。`取代` 只表示旧决定整体失效，必须在旧 ADR 的 `被取代` 中反向登记。部分补充、
实验恢复或适用范围变化写入正文关联，不改变旧 ADR 状态。

Accepted 正文不可静默改写。允许修复失效链接、补充反向取代元数据或增加明确勘误；新的决定
必须新增 ADR。ADR 0009 是“接受拒绝旧 Rudin 路线”的决定，因此保持 Accepted；ADR 0010 的
限定试跑不完整取代该失败结论。

## 维护流程

1. 使用模板创建 Proposed ADR，分配下一个编号并登记 README。
2. 冻结背景、候选方案、决定、后果和关联证据；需要实验时先完成实验治理。
3. 接受或拒绝后同步状态、索引、关联架构/设计与实施计划。
4. 完整取代时同步新旧 ADR 的双向元数据，旧 ADR 标记 Superseded 且保持原路径。
5. 运行 ADR 结构、Markdown 链接和代码映射测试。
